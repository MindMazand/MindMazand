# مرحله چهارم — پیاده‌سازی شش محور عملیاتی

## محدوده این مرحله
این مرحله شش محور برنامه‌ریزی‌شده را در سورس WPF تکمیل می‌کند:
1. مدیریت اشخاص و ایجاد سریع طرف حساب
2. مدیریت گروه محصول، محصول، بسته‌بندی و انبار
3. اتصال فهرست‌های انتخابی به جداول مرجع و پشتیبانی ورود کد/نام
4. ثبت باسکول ورودی و خروجی با محاسبه وزن خالص
5. صف بررسی و تأیید مدیر و قطعی‌سازی گردش موجودی
6. داشبورد مبتنی بر اسناد تأییدشده و نمودار هفت‌روزه

## قواعد محاسبات باسکول
- واحد ذخیره‌سازی وزن: گرم صحیح (INTEGER).
- ورودی UI: کیلوگرم با حداکثر سه رقم اعشار.
- وزن ظرف از `packaging_types.tare_weight_g` خوانده و در سند Snapshot می‌شود.
- وزن قبل از افت = وزن ناخالص − وزن ظرف.
- وزن افت = گرد کردن وزن قبل از افت × نرخ افت بر حسب basis point.
- وزن خالص = وزن قبل از افت − وزن افت.
- تعداد سبد مثبت بدون انتخاب نوع بسته‌بندی مجاز نیست.
- طرف حساب، محصول و انبار برای سند باسکول اجباری‌اند.

## گردش موجودی
- باسکول ورودی یک Lot و یک Stock Movement مثبت در وضعیت Pending ایجاد می‌کند.
- باسکول خروجی از موجودی تأییدشده همان محصول و انبار به روش FIFO تخصیص می‌گیرد و Movement منفی Pending می‌سازد.
- هیچ Movement تا تأیید مدیر Posted نمی‌شود.
- Migration 003 یک Trigger برای جلوگیری از منفی شدن موجودی در لحظه Posting اضافه می‌کند.
- تأیید سند و قطعی‌سازی Movementها در یک تراکنش SQLite انجام می‌شود؛ خطا موجب Rollback می‌شود.

## تأیید
- فقط نقش ADMIN یا MANAGER مجاز است.
- سند باید در وضعیت REVIEW باشد.
- تاریخچه وضعیت و هویت تأییدکننده ذخیره می‌شود.
- سند قطعی بدون سند اصلاحی/برگشت قابل ویرایش نیست.

## داشبورد
- وزن ورودی و خروجی فقط از اسناد APPROVED خوانده می‌شود.
- فروش از مبلغ خطوط اسناد SALE تأییدشده خوانده می‌شود.
- مانده خالص اشخاص از خطوط دفترکل Posted محاسبه می‌شود.
- شمار اسناد بررسی و چک‌های سررسید گذشته جداگانه نمایش داده می‌شوند.
- نمودار هفت‌روزه از توزین‌های تأییدشده ساخته می‌شود؛ داده آزمایشی یا ساختگی ندارد.

## محدودیت اجرایی
سورس WPF به دلیل نبود MSBuild/.NET Framework Developer Pack در محیط ساخت فعلی کامپایل نشده است. تست SQL و تست‌های خودکار Python موفق‌اند؛ Build نهایی و آزمون UI باید روی Windows انجام شوند.
